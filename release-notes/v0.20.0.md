# Khaos Nexus v0.20.0

## Game Adapter SDK foundation

This guarded candidate establishes the shared server-integration contract required before adding Rust, Satisfactory, 7 Days to Die, Minecraft Bedrock, DayZ and other researched game modules.

### Typed capability manifests

Every adapter now declares:

- a stable adapter and game identity;
- transport and adapter version;
- supported operations;
- minimum viewer, operator or Owner access;
- destructive-action classification;
- bounded operation timeout;
- optional dry-run support;
- redacted public metadata.

The application no longer needs to infer server controls from a game-name string. Future interfaces can display only capabilities that the selected adapter explicitly supports.

Custom, game-specific capabilities must declare their own access role and destructive-action policy. They cannot silently inherit permissive viewer access.

### Standard operation contract

The SDK recognizes shared status, health, information, player, metric, settings, announcement, save, backup, moderation, shutdown, restart, stop, raw command, world-data, log and configuration capabilities.

Game-specific capabilities may be namespaced, such as `rust.queue`, while still using the same access, timeout, error and audit boundaries.

### Stable error and execution model

Operations now receive:

- unique request IDs;
- start and finish timestamps;
- measured duration;
- adapter, game and capability context;
- stable error codes;
- retryable classification;
- automatic timeout and cancellation handling.

Transport exceptions are normalized into public-safe errors including `AUTH_FAILED`, `CONNECTION_FAILED`, `TIMEOUT`, `RATE_LIMITED`, `CAPABILITY_UNSUPPORTED`, `ACCESS_DENIED` and `SECURITY_POLICY`.

Timeout and cancellation errors retain the adapter and capability identity needed for useful diagnostics.

### Secret-safe results

Adapter output always redacts:

- passwords;
- tokens and API keys;
- authorization values;
- cookies and sessions;
- credentials and private keys;
- RCON secrets;
- explicitly supplied protected values.

Operational payloads are not truncated. Large Palworld world-data exports and future save/telemetry results retain their complete arrays and strings after redaction.

### Opt-in fixture recorder

A bounded JSONL fixture recorder is available for adapter development and protocol compatibility tests.

It is disabled by default and requires both an explicit enable flag and a destination directory. It provides:

- recursive credential redaction;
- bounded depth, fields, arrays and strings;
- oversized-record previews;
- size-based rotation;
- per-adapter listing and clearing;
- Date or numeric test clocks.

Fixture truncation applies only to diagnostic samples, never to live operation results.

### Current transport bridge

Existing server transports now advertise real capabilities through the SDK:

- **Palworld REST:** typed status, players, information, metrics, settings, announcements, saves, moderation, shutdown and world-data operations; raw commands remain unavailable.
- **ARK RCON:** status, players, announcements, saves, moderation, shutdown and Owner-only raw commands; unsupported unban is not advertised.
- **Generic and Palworld legacy RCON:** capabilities are derived from the existing safe command map.

### First migrated consumers

- Palworld desktop operations execute through the adapter SDK after their existing input and shutdown confirmation checks.
- Discord server-status panels use adapter operations for status and player checks.
- Existing injected transport factories remain supported for deterministic tests.

## Security boundaries

This release does not:

- add a public network listener;
- enable Mobile Companion networking;
- expose fixture recording in normal production use;
- permit raw commands on Palworld REST;
- weaken Owner module switches;
- weaken shutdown or force-stop confirmations;
- move server credentials into renderer state;
- claim that researched future games are already supported.

## Preserved v0.19.0 foundations

- authoritative Owner enable/disable controls;
- Disable All, Safe Mode and Enable Validated;
- dependency-aware blocked state;
- module-aware Discord commands and buttons;
- complete supervised Discord runtime entry chain;
- protected Owner authentication recovery;
- high-severity production dependency audit;
- Windows installer and portable executable verification;
- startup, watchdog, navigation, updater, backup and monitoring repairs.

Stable publication remains blocked until the exact final source checkpoint passes the complete Linux and Windows validation pipelines and the Owner confirms startup and existing server behavior on the production PC.
